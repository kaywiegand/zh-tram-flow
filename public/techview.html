Datenstrategie

Vier Quellen, ein temporaler Join, 94,4 Millionen Zeilen
VBZ IST-Daten
  • Reale Ankunfts- und Abfahrtszeiten aller Tramhalte 2023–2025
  • Granularität: jede Fahrt × jede Haltestelle × Timestamp
  • canceled = True Fahrten bewusst behalten — relevante Extremfälle
GTFS (Fahrplandaten)
  • Geplante Zeiten, dwell_time, stop_sequence, Liniengeometrien
  • Ermöglicht: arrival_delay = IST − SOLL
  • Join-Key: trip_id × stop_id × service_date
Meteo Schweiz
  • Stündliche Messwerte: Temperatur, Niederschlag, Windgeschwindigkeit
  • Abgeleitete Flags: has_rain, has_snow, has_heavy_rain, is_hot
  • Join über Zeitstempel auf Stundenbasis
Event-Kalender + Ergebnis
  • Grossveranstaltungen 2023–2025: Konzerte, Messen, Sport, Feiertage
  • Kategorisierung: event_type, event_size, event_weight
  • 94,4 Mio. Zeilen · 26 Features · 541 MB Parquet

Datenstrategie

Cleaning als Forschungsentscheidung, nicht als Routine
Canceled-Fahrten entfernen
→
Behalten: canceled = True sind Extremfälle, die das Modell kennen muss. Entfernen würde die Realität verfälschen.
Shuffle-Split für mehr Trainingsdaten
→
Temporal Split: Zukunft darf Vergangenheit nicht kennen. Shuffle erzeugt Data Leakage.
One-Hot Encoding für Kategorien
→
LightGBM native Categoricals: stop_name, line_name direkt als Kategorie. Weniger Speicher, schnelleres Training.
arrival_delay winsorisieren
→
Kein Capping: MAE bestraft Extremwerte proportional. Winsorisierung würde Systemfehler verbergen.

Feature Engineering

34 Features in v1, 36 in v2 — zwei neue Features erklären −63 % MAE
Temporale Features (v1)
  • hour, weekday, month, season, year
  • is_weekend, is_november, is_holiday
  • is_late_night_weekend (Kombi-Feature)
Netz-Features (v1)
  • line_name, stop_name (native categoricals)
  • district_nr, n_lines_at_stop, n_stops_line
  • is_start_stop, is_end_stop, dwell_time
Externe Features (v1)
  • temperature, precipitation, wind_speed
  • has_rain, has_heavy_rain, has_snow, is_hot
  • has_event, event_type, event_size, event_weight
Kaskaden-Features (neu in v2)
  • prev_trip_delay: Verspätung des Vorgänger-Trips, echtzeit-verfügbar
  • stop_sequence_pct: normierter Streckenfortschritt (0–1), linienübergreifend lernbar
  • Ergebnis: MAE 45,7 s → 18,56 s (−31,4 s)

Modellauswahl und -Anpassung

Warum LightGBM, warum kein Hyperparameter-Tuning
XGBoost als Standard-Benchmark
→
XGBoost: val MAE ~21,4 s bei 150 Runden, über 90 Minuten Trainingszeit. LightGBM: 18 Minuten für vergleichbare Qualität.
One-Hot Encoding für Kategorien
→
LightGBM native Categoricals. Weniger Speicher, schnelleres Training, keine Sparsität.
Hyperparameter-Tuning vor Feature Engineering
→
Bewusst zurückgestellt: Feature Engineering bringt mehr als Tuning. prev_trip_delay liefert allein −27s MAE.
Feste Anzahl Runden wählen
→
Early Stopping mit Validation-Set steuert Komplexität automatisch. Verhindert Overfitting ohne manuelle Suche.

Feature Importance

prev_trip_delay dominiert, die Analyse hat recht behalten
📊Feature Importance LightGBM v2Export ausstehend
Feature Importance (Gain). prev_trip_delay und stop_sequence_pct dominieren.
Top-Features bestätigen die EDA: prev_trip_delay ist stärkstes Feature. stop_sequence_pct an zweiter Stelle.
Temporale Features (hour, weekday, month) zeigen konsistente, aber deutlich schwächere Beiträge. Wetter-Features stabil vorhanden.
Das Signal steckte in den Daten, nicht im Algorithmus. Die Kaskadenanalyse (r ≥ 0.85) hat die Feature-Wichtigkeit korrekt antizipiert.

Produktionsreife und Reflexion

Was produktionsreif ist, was offen bleibt
Produktionsreif
→
LightGBM v2: MAE 18,56 s, MBE −0,69 s, trainiert auf 41M Fahrten, getestet auf vollständigem Jahr 2025 (~29 M). Streamlit-Dashboard lauffähig.
Offen: Hyperparameter-Tuning
→
Bewusst zurückgestellt. Nächster Schritt. Potenziell weitere −2 bis −4s MAE erreichbar.
Offen: v2 im Streamlit-Predictor
→
Dashboard nutzt aktuell v1. v2 erfordert Live-Signal aus VBZ-Betriebssystem.
Offen: Ensemble / Stacking
→
Nicht evaluiert. LightGBM v2 liefert bereits −63% vs. Baseline. Nächste Iteration nach Tuning.
